# 软件设计原则

> 文档状态：已生效，强制评审  
> 适用范围：模块、类型、公开 API、领域规则与重构  

## 1. 目标

设计原则用于判断职责、依赖和变化边界是否合理，不是要求增加接口、继承层次或抽象数量。安全、隐私、数据完整性、隔离边界和已发布契约优先于形式上的 SOLID。

默认采用 KISS 和 YAGNI：能由直接类型、数据库约束或一个清晰方法解决的问题，不先创建框架。只有重复已经代表同一知识且会共同变化时才应用 DRY；相似代码但业务语义不同，不强行抽取。

## 2. SOLID 的工程化解释

### 2.1 单一职责原则（SRP）

一个类型只有一个主要变化原因，不等于一个类只有一个方法。

符合：

- Controller 只处理 HTTP 协议和可信身份转换；
- Application Service 负责一个或一组高度内聚的用例；
- Domain Policy 负责确定性业务规则；
- Persistence Adapter 负责 owning module 的持久化；
- 外部 Adapter 负责协议、供应商 DTO、Secret 和错误转换。

需要拆分的信号：同一个类因互不相关产品需求反复修改、构造器依赖来自多个无关模块、私有方法形成多个独立流程、测试一个规则要 Mock 大量无关协作者。禁止只按行数或方法数量机械拆分。

### 2.2 开闭原则（OCP）

稳定边界应允许新增实现而不破坏调用方，但普通业务规则可以直接修改并测试。OCP 不等于“任何需求都新增子类”。

- 已有两个以上真实算法、供应商或渠道时使用窄 Strategy/Adapter 扩展；
- 状态机新增合法转换时修改 owning Policy，而不是用继承隐藏规则；
- 新业务字段按兼容契约和数据库演进直接增加；
- 不为“未来可能”预建 SPI、Factory、插件注册表或反射扫描。

### 2.3 里氏替换原则（LSP）

实现必须遵守 Port/父类型的前置条件、后置条件、幂等、错误和安全语义：

- 子实现不能要求调用方提供更强的前置条件；
- 不能放宽返回值不变量或改变金额、Scope、租户边界；
- 不能把明确拒绝改成静默成功或把幂等操作改为重复副作用；
- 供应商差异在 Adapter 内转换为平台稳定结果。

替换性必须通过共享 Contract Test 验证；仅能编译不代表满足 LSP。

### 2.4 接口隔离原则（ISP）

调用方只依赖它使用的最小能力：

- 按用例定义窄查询/命令 Port，避免万能 Repository 和胖 Service；
- 读模型不依赖写命令；一个边界的身份模型不依赖无关业务 API；
- 模块公开面只暴露稳定命令、查询结果和事件，不泄漏内部持久化类型。

接口过细导致每个实现只有一行转发时，应合并回直接调用；ISP 不要求“一方法一个接口”。

### 2.5 依赖倒置原则（DIP）

业务规则不依赖 Web、数据库或供应商细节；依赖方向指向稳定策略和 owning module 的公开面。

- Domain 不依赖 Web/数据库框架、网络客户端或供应商 SDK；
- Application 通过语义 Port 调用数据库/外部系统，Port 只有在隔离边界真实存在时创建；
- Infrastructure 实现 Port 并完成协议转换；
- 模块之间依赖公开 API，不依赖对方 application/domain/infrastructure。

DIP 不等于每个类都配一个接口。内部确定性服务只有一个实现且无隔离价值时直接使用具体类型。

## 3. 其他强制原则

### 3.1 高内聚、低耦合

- 数据和维护其不变量的行为属于同一 owning module；
- 跨模块只传稳定值，不共享可变对象、事务或基础设施类型；
- 一项需求应尽量集中修改少数内聚文件，而不是横切所有模块；
- 循环依赖表示边界错误，不能用事件、全局工具或反射掩盖。

### 3.2 组合优于继承

- 组件、策略和适配器优先通过组合协作；
- 继承只用于真实 is-a 关系且替换性有测试；
- 禁止 BaseController、BaseService、模板 Repository 和为了复用几行代码建立的抽象父类。

### 3.3 显式优于隐式

- Tenant/Subject/Resource、金额、币种、Scope、幂等键和时间来源显式进入命令/值类型；
- 不从 ThreadLocal、全局静态变量或字符串约定偷偷取得领域事实；
- 默认值、安全降级和重试必须在配置/契约中可见；
- 结果未知保持可对账事实，不假装失败或成功。

### 3.4 不变量下沉

- 单请求输入用 Bean Validation/类型构造器；
- 领域合法转换用 Policy/状态机；
- 跨请求唯一性、租户一致性和金额事实用数据库约束/条件更新；
- 安全授权在可信身份和持久化边界交叉校验，不能只放 Controller。

## 4. 常见误用

| 误用 | 问题 | 正确处理 |
|---|---|---|
| 为 OCP 给每个服务建接口 | 单实现抽象增加导航成本 | 外部边界或第二个真实实现出现时再抽象 |
| 为 SRP 把类拆成大量一行委托 | 职责没有真正分离 | 按变化原因和用例簇拆分 |
| 为 DRY 合并相似业务流程 | 不同规则被耦合 | 只共享稳定、同语义知识 |
| 用继承复用 Controller/Service | 隐藏依赖和授权 | 使用组合或纯函数 |
| 用事件消除所有直接依赖 | 时序和失败语义变隐式 | 强一致用公开服务；真正通知才用事件 |
| 为 Clean Architecture 建空包/空接口 | 只有形式没有边界 | 只有真实复杂度到来时创建层次 |

## 5. 评审清单

- [ ] 每个类型和模块有明确变化原因与数据所有权。
- [ ] 新抽象对应现有第二实现、外部边界或测试隔离，而非猜测未来。
- [ ] Port 实现满足相同前置、后置、错误、幂等和安全语义。
- [ ] 接口没有强迫调用方依赖无关能力，也没有碎成一行转发。
- [ ] 依赖由 Web/DB/供应商细节指向用例和领域，而不是反向。
- [ ] 不变量落在能够跨请求保证它的最低可靠层。
- [ ] 设计比直接方案更容易理解和验证；否则退回简单实现。

# Git 提交与协作规范

## 1. 基本原则

- 主分支、远端、保护规则和集成方式由采用项目声明。多人协作时从最新受保护基线创建短期分支；没有远端时不虚构远端流程。
- 一个提交只完成一个内聚目标，代码、测试、迁移和相应文档必须一起提交。
- 工作区已有修改属于其作者；禁止用 reset、restore、checkout、stash 或 clean 处理不属于当前任务的修改。
- 不 force push，不重写已共享历史，不用自动 `ours/theirs` 策略吞掉冲突。
- Commit、合并、推送和发布是不同动作；没有明确授权不推送或发布。

## 2. 分支

有远端后使用短期分支：

```text
feat/<work-package>
fix/<work-package>
docs/<work-package>
chore/<work-package>
```

分支名使用小写 kebab-case。开始工作前以只读方式确认工作区、当前分支和远端基线。共享分支不 rebase、不重写；项目可以允许低风险维护直接提交本地集成分支，但高风险变化应在短期分支形成精确 Commit 并复核。规范不追溯重写已有历史。

## 3. Commit Message

格式采用 Conventional Commits：

```text
<type>(可选 scope): 中文摘要
```

允许类型：

| type | 用途 |
|---|---|
| `feat` | 新增用户或业务能力 |
| `fix` | 修复缺陷、安全或数据问题 |
| `docs` | 仅文档 |
| `refactor` | 行为不变的结构调整 |
| `test` | 仅测试或测试基础设施 |
| `perf` | 有证据的性能改进 |
| `build` | Gradle、依赖、制品 |
| `ci` | CI/CD 配置 |
| `chore` | 其他维护 |
| `style` | 仅格式，不改变语义 |
| `revert` | 回退既有提交 |

摘要使用祈使语义、具体且不加句号，中文为主，Java、Gradle、API 等技术名保留英文。禁止 `WIP`、`update`、`misc`、`fix bug` 等无信息主题。

示例：

```text
feat(billing): 增加额度预占与结算
fix(auth): 阻止暂停订阅交换登录凭据
docs(development): 增加 Java 和架构规范
build: 启用 Checkstyle 与架构门禁
```

破坏性契约变更在正文写 `BREAKING CHANGE:`，并同步版本、迁移和发布文档。关联需求可在正文写 `Refs: TASK-123`；安全修复不要在公开摘要泄漏可利用细节。

## 4. 提交粒度

应在同一提交：

- 实现及其单元/集成/安全测试；
- Migration 与相应 Codegen 输入、持久化实现和迁移测试；
- API/事件/Schema 变更与契约、示例和兼容文档；
- 包边界变化与模块/架构规则。

不应混在同一提交：

- 无关格式化或重命名；
- 多个独立业务功能；
- 本地 IDE、日志、构建产物、Secret 或个人配置；
- 为了让测试通过而顺手修改的无关规则。

只有代码和测试共同构成目标时，不为追求“一文件一提交”拆开。大规模机械重命名与行为变化应分开，便于评审真实逻辑。

## 5. 提交前检查

每次提交按顺序执行：

1. `git status --short`，确认没有用户无关修改；
2. 只暂存当前目标路径，避免宽泛纳入未知文件；
3. `git diff --cached --check`；
4. 阅读完整 staged diff，而不只看统计；
5. 执行风险相称的验证；
6. 检查 Secret、真实生产配置、Token、私钥、日志和构建产物；
7. 再次确认 staged 文件和 Commit Message。

验证矩阵：

| 变更 | 最小验证 |
|---|---|
| Markdown | 围栏、JSON/YAML 示例、相对链接、`git diff --check` |
| Java 逻辑 | 编译、Checkstyle、直接单元测试 |
| 包/模块/依赖 | `architectureCheck`、Modulith、受影响模块测试 |
| Migration/Codegen | 实际数据库空库迁移、生成、升级和数据库集成测试 |
| API/事件 | OpenAPI/Schema/契约测试和兼容检查 |
| 租户/资源、安全 | 真实身份的正向与越权负向测试 |
| 额度/支付/幂等 | 实际数据库并发、重复、结果未知和补偿测试 |
| 构建/版本 | 项目统一检查入口和受影响制品构建 |

只报告实际运行的检查。`UP-TO-DATE` 或缓存结果只有在输入与环境未变化时可复用；失败不能包装成成功。

## 6. 高风险变更

以下变更合并前需要独立只读复核：

- 登录、Token、Scope、跨租户/资源授权；
- 支付、账单、额度、用量和幂等；
- Secret、Webhook 验签、SSRF 和外部回调；
- 破坏性 Migration、数据回填和恢复工具；
- API/Event 跨系统路由；
- 生产发布权限与基础设施。

复核绑定精确 Commit 和 diff，记录阻断级与高优先级问题、已执行测试和残余风险。普通文档或低风险重构不要求建立重型候选包或安全红队流程。

## 7. 合并与冲突

- 合并前更新目标基线并重新判断依赖、契约、迁移和测试影响。
- 无文本冲突不等于无组合风险；对共享表、契约、模块边界和版本目录做额外检查。
- 冲突由理解对应业务语义的人处理；解决后相关测试和高风险复核失效，必须重跑。
- 禁止 `git reset --hard`、宽泛 `git clean`、`git checkout --` 和强制推送修复协作问题。
- 已共享提交不通过 rebase/cherry-pick 冒充原审查对象；需要改变字节时形成新提交并重新验证。

## 8. 推送

推送只在用户或工作流程明确授权后执行，且使用普通非强制 push。推送前再次读取远端基线；结果不明时停止自动重试，先只读确认远端 Ref。推送后 read-back 并报告远端 Commit。

禁止：

- `--force`、`--force-with-lease`、`+refspec`；
- 删除或覆盖共享分支；
- 未经授权创建 PR、Tag、Release 或触发生产部署；
- 为了通过保护规则删除测试、架构门禁或审计证据。

## 9. 完成报告

交付时简要说明：

- 完成结果和关键文件；
- Commit ID 与主题（若已提交）；
- 实际运行并通过的验证；
- 未运行项及原因；
- 工作区是否干净；
- 是否推送（未授权时明确“未推送”）。

## 10. 检查清单

- [ ] Commit 目标单一，消息符合 `<type>(scope): 摘要`。
- [ ] 暂存区没有无关文件、IDE、构建产物或 Secret。
- [ ] 完整 staged diff 已阅读，`git diff --cached --check` 通过。
- [ ] 风险相称的测试和架构门禁通过。
- [ ] 契约、迁移、测试和文档与实现同步。
- [ ] 共享历史未被重写，用户修改未被丢弃。
- [ ] 未经授权没有推送、发版或外部写操作。

# 数据结构与算法使用规范

> 文档状态：已生效，按场景强制选择  
> 原则：标准库和数据库优先，不重复实现基础算法  

## 1. 目标

数据结构和算法负责时间、空间、顺序、唯一性和容量，不负责替代架构边界。日常业务开发默认使用 JDK、所选数据库和查询工具的成熟实现，不手写红黑树、排序、缓存或队列；只有现有能力无法满足并有测量证据时才自定义。

选择前必须明确：数据规模、读写比例、是否需要顺序/重复、查询方式、并发模型、内存上限和失败恢复。没有上限的数据结构视为缺陷。

## 2. Java 集合选择

| 需求 | 首选 | 说明 |
|---|---|---|
| 有序、允许重复 | `ArrayList` / `List` | 默认顺序集合，随机访问友好 |
| 队列/双端队列/栈 | `ArrayDeque` | 不使用旧 `Stack`，不默认 `LinkedList` |
| 唯一、无顺序 | `HashSet` | 需要稳定迭代顺序时用 `LinkedHashSet` |
| 枚举集合/键 | `EnumSet` / `EnumMap` | 封闭键空间、内存紧凑 |
| Key → Value 索引 | `HashMap` | 需要插入顺序时用 `LinkedHashMap` |
| 排序/范围查询 | `NavigableSet` / `NavigableMap` | 只有需要 floor/ceiling/range 时使用 |
| 优先级/临时 Top-K | `PriorityQueue` | 不承担可靠延时任务 |
| 复合键 | 不可变 `record` | 禁止字符串拼接租户、主体和资源 ID |
| 不可变边界 | `List.copyOf`/`Set.copyOf`/`Map.copyOf` | 顺序是契约时返回明确有序 List |

- 自定义对象作为 Set 元素或 Map Key 前必须有稳定值相等语义；普通类成对实现 `equals/hashCode`，只使用生命周期不变字段。
- 重复如果代表配置/契约错误，必须失败，不能用 Set 或 merge function 静默去重。
- 数组只用于底层二进制/性能边界；跨模块和 record 使用防御性不可变封装。
- `LinkedList` 只有真实中间节点操作证据时使用；普通追加、遍历和队列分别选择 `ArrayList`/`ArrayDeque`。

## 3. 并发结构

| 结构 | 允许 | 禁止 |
|---|---|---|
| `ConcurrentHashMap` | 节点内、非权威、可重建索引 | 数据库/网络 I/O 放入 `compute`；承担配额/幂等 |
| `Atomic*` | JVM 内简单状态 | 分布式序列、额度、账务 |
| `LongAdder` | 近实时指标 | 精确业务计数 |
| `Semaphore` | 限制单节点远程服务/昂贵资源并发 | 替代集群授权或额度 |
| `BlockingQueue` | 有容量、可丢失的节点内协调 | 可靠 Worker 队列 |
| `CompletableFuture` | 少量独立只读调用 | commonPool、无超时、事务内 fan-out |

多副本权威事实使用数据库唯一约束、复合外键、条件更新、行锁、任务表或可靠消息系统。Java Lock、Map 或队列不能替代分布式事实。

## 4. 数据库与内存分工

- 过滤、关联、存在性、唯一、排序、聚合、分页优先由数据库和参数化查询工具完成。
- 禁止加载全表到 Java 再搜索、排序、去重或分页；查询只选需要的列并设置硬上限。
- 避免 N+1：使用 Join、批量 `IN`、聚合或一次批量读取，再用有界 Map 组装。
- API 列表使用稳定排序和游标/分页；批处理读取 `limit + 1` 或固定 batch，不使用无界 `findAll`。
- 数据库负责跨请求一致性，内存只保存可重建、非权威、容量受限的临时数据。
- 缓存不是默认答案。只有测量证明数据源或计算成为瓶颈，并定义一致性、失效、容量和降级后才引入本地或分布式缓存。

## 5. 常用算法选择

### 5.1 排序与 Top-K

- 普通内存排序使用 `List.sort`/Stream `sorted`，不手写快排/归并。
- 数据来自数据库时优先 `ORDER BY` + 合适索引 + `LIMIT`，避免全量回传。
- 稳定顺序是分页契约的一部分，排序键必须唯一或追加唯一 tie-breaker。
- 小型有界 Top-K 可使用 `PriorityQueue`；长期排行榜、跨节点统计使用数据库或专门系统并先提供需求证据。

### 5.2 搜索

- 精确 Key 查找使用 Map/数据库唯一索引；范围查找使用有序索引/Navigable 结构。
- 有序内存列表可以使用 `Collections.binarySearch`，但数据频繁变化时不要为二分查找维护昂贵复制。
- 组合列表搜索使用白名单条件模型，由查询工具拼装参数化语句；禁止把用户输入拼成 SQL、字段名或任意表达式。
- 文本搜索先使用已选数据库的索引能力；只有真实规模和语言需求超过后再评估专用搜索引擎。

### 5.3 图与依赖

- 模块依赖、契约引用和工作流关系可以建模为邻接表，使用 DFS/BFS 做可达性/环检测；优先复用已有模块、契约或校验工具。
- 禁止把普通父子关系或状态机过度建成通用 Graph Engine。
- 图遍历必须有节点/深度上限和 visited 集，防止循环与资源耗尽。

### 5.4 字符串匹配

- 普通精确/前缀判断使用 JDK 或数据库索引；不手写 KMP。
- Trie 只在大量静态前缀且性能测量证明普通索引不足时使用，不为未来搜索提示预建。
- Regex 来自固定代码或受限模板；用户输入不得直接成为高复杂度正则，必须限制长度和执行成本。

### 5.5 重试与退避

- 重试算法使用有上限的指数退避 + 抖动 + 总时限，只重试可重试且幂等的操作。
- 不用 `Thread.sleep` 实现测试等待或占用 Worker；调度时间持久化到任务事实。
- 结果未知进入对账/查询，不通过无限重试猜测结果。

## 6. 复杂度与容量检查

评审非平凡循环、批处理和查询时至少回答：

1. 输入最大规模是多少，硬上限在哪里；
2. 时间复杂度是否随数据量线性、对数或平方增长；
3. 是否重复扫描、嵌套查找或出现 N+1；
4. 内存是否同时保留原始、转换和索引三份数据；
5. 并发时数据库连接、线程、远程调用和日志是否放大；
6. 超限时是分页、拒绝、降级还是异步处理；
7. 指标/压测如何证明优化有效。

不要为几十条有界数据做微优化；也不要用“数据暂时少”解释无界 API、全表扫描或 O(n²) 热路径。

## 7. 时间、金额与标识值

- 领域时间依赖注入 `Clock`；数据库事实时间使用同一事务来源，不在深层散落 `Instant.now()`。
- 时间点使用 `Instant`；展示时区在边界转换；账期等业务日期使用 `LocalDate` 并明确时区。
- 金额使用最小货币单位整数或 `BigDecimal`，显式币种和 rounding mode，禁止 `double/float`。
- 对外 ID 是不透明字符串；内部 UUID 不向外承诺编码版本。
- `tenantId`、`subjectId`、`resourceId` 等容易混淆的标识使用专用值类型或复合键。

## 8. 性能验证

- 先定位瓶颈，再优化；优先看 SQL 数量/计划、I/O、p95/p99、CPU、RSS 和 GC。
- 数据库查询使用代表性数据验证索引和计划；小型单元测试不能证明性能。
- JMH 只用于纯 JVM 热点；不能用微基准证明数据库/网络链路优化。
- 优化必须保留等价正确性测试、容量上限和回退方式。
- 无测量依据不引入缓存、并行流、自定义集合、专用搜索或分布式计算。

## 9. 评审清单

- [ ] 数据规模、顺序、重复、并发和容量上限明确。
- [ ] 使用标准库、数据库和已选查询工具，没有重复实现基础算法。
- [ ] 集合选择符合访问模式和值相等语义。
- [ ] 过滤、排序、聚合和分页在数据库完成，没有全表加载/N+1。
- [ ] JVM 本地结构没有承担分布式权威事实。
- [ ] 搜索、图遍历、Regex、批次和重试有资源上限。
- [ ] 优化有测量、正确性测试和回退方案。

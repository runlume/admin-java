# 设计模式使用规范

> 文档状态：已生效，按需使用  
> 模式目录：GoF 23 种设计模式完整清单  
> 原则：模式解决真实变化点，不按数量考核  

## 1. 选择规则

GoF 标准设计模式共 23 种：创建型 5 种、结构型 7 种、行为型 11 种。本文完整列出它们，是为了统一识别和选择，不表示代码必须使用全部模式。

使用模式前必须回答：当前问题和变化点是什么、直接代码哪里不足、候选模式解决哪一项职责、增加了哪些类型、如何测试。回答不清时不引入模式。

选择顺序：

1. 直接构造、普通方法或清晰的 `switch`；
2. 语言标准库、框架和数据库已有能力；
3. 代码库中已经使用且边界一致的模式；
4. 最小、明确的 GoF 或企业应用模式。

同一问题可能符合多个模式，只选择能消除当前主要变化点的最小组合。禁止为展示“设计感”增加抽象，也禁止看到名称相似就机械套用模式。

## 2. GoF 创建型模式（5 种）

| 模式 | 适用条件 | 选择与约束 |
|---|---|---|
| Factory Method（工厂方法） | 创建过程随具体类型变化，调用方只依赖抽象产品 | Aggregate 创建具有真实分支时使用；简单 record/值对象直接构造 |
| Abstract Factory（抽象工厂） | 需要创建一组必须相互兼容的产品族 | 只有产品族及兼容关系真实存在时使用，不为未来供应商预建接口 |
| Builder（建造者） | 可选参数多、构造步骤需要可读性或分阶段校验 | 优先用于复杂测试数据或配置；业务必填不变量仍由最终类型校验 |
| Prototype（原型） | 从既有对象复制新对象比重新构造更合适 | 优先不可变对象显式复制，禁止 `Cloneable` 浅拷贝领域对象 |
| Singleton（单例） | 一个进程只需一个无状态共享实例 | 由依赖注入容器或语言初始化机制管理；禁止全局可变实例和 Service Locator |

创建型模式不能隐藏数据库、网络、权限、事务或 Secret 获取。构造需要 I/O 时由 Application Service/Adapter 先取得事实，再显式创建对象。

## 3. GoF 结构型模式（7 种）

| 模式 | 适用条件 | 选择与约束 |
|---|---|---|
| Adapter（适配器） | 外部接口与内部稳定接口不兼容 | 适用于支付、AI、身份、邮件和远程系统；供应商 DTO/异常/Secret 留在 Adapter |
| Bridge（桥接） | 抽象与实现存在两个独立变化维度，需要分别演进 | 只有两个维度都已有真实变化时使用，不能替代简单组合 |
| Composite（组合） | 单个对象与对象树需要用统一方式处理 | 只用于真实树形结构；普通列表、状态机和模块关系不建通用节点树 |
| Decorator（装饰器） | 不修改核心实现即可叠加可组合职责 | 可用于指标、审计、限流等稳定横切能力；顺序必须明确，不隐藏授权、事务或金额规则 |
| Facade（外观） | 需要为复杂子系统提供稳定、窄的入口 | 模块公开 API 可以作为 Facade；不能演化为承担全部用例的 God Service 或一层空转发 |
| Flyweight（享元） | 大量细粒度对象共享相同不可变状态，内存收益可测量 | 只有内存剖析证明必要时使用，租户/用户等可变事实禁止共享 |
| Proxy（代理） | 需要在访问目标前后执行授权、路由或远程访问控制 | 目标必须从可信配置/授权关系解析，调用方不能借代理访问任意 URL |

Adapter 只有一个实现时也必须具有真实协议隔离价值。Bridge、Composite、Flyweight 没有当前使用者时不预建类型。

## 4. GoF 行为型模式（11 种）

| 模式 | 适用条件 | 选择与约束 |
|---|---|---|
| Chain of Responsibility（职责链） | 多个独立步骤按确定顺序处理，可中止或继续 | 用于已有稳定校验/处理步骤；顺序、停止条件和错误聚合明确，禁止字符串万能 Pipeline |
| Command（命令） | 请求需要作为对象传递、持久化、排队、审计或重试 | 生命周期、升级和可靠操作可使用明确 Command/Operation；命令必须有身份、幂等键和状态，不做万能命令总线 |
| Interpreter（解释器） | 存在规模受限、语法稳定的领域语言 | 过滤优先强类型条件和参数化查询，复杂表达式有真实需求后再自建 DSL |
| Iterator（迭代器） | 需要隐藏集合内部结构并顺序访问元素 | 默认使用 JDK Iterator/Stream 或分页游标；不为数据库全表扫描编写自定义 Iterator |
| Mediator（中介者） | 多个对象互相依赖，需要集中协调交互 | Application Service 可协调一个用例；禁止全局 EventBus/Mediator 接管所有模块调用 |
| Memento（备忘录） | 需要保存并恢复对象先前状态且不暴露内部实现 | 升级/审核需要时保存版本化不可变快照；禁止在内存复制完整 Aggregate 冒充可靠恢复 |
| Observer（观察者） | 一项已发生事实需要通知多个订阅者 | 同进程、无需崩溃恢复时使用 Modulith Event；可靠外部投递必须升级为 Outbox/Delivery |
| State（状态） | 对象行为随有限状态变化且非法转换需要集中控制 | 简单状态优先 enum+穷尽规则，行为足够复杂时再使用状态对象，不机械一状态一类 |
| Strategy（策略） | 多个算法/渠道在相同契约下可互换 | 第二个真实算法/渠道出现后使用 Strategy+Registry；一个实现不预建插件框架 |
| Template Method（模板方法） | 多个实现共享稳定步骤骨架，少数步骤允许覆盖 | 优先组合；只有真实继承和替换性测试时使用，禁止 BaseService 模板层级 |
| Visitor（访问者） | 封闭对象结构稳定，但需要频繁增加跨类型操作 | 只有 sealed/稳定结构且操作维度频繁增长时使用，普通映射直接方法处理 |

## 5. 企业应用补充模式

以下是常见架构/企业应用模式，不计入 GoF 23 种，仍需按场景选择：

| 模式 | 使用场景 | 关键约束 |
|---|---|---|
| Port and Adapter | 外部协议和持久化边界 | Port 由用例拥有；没有隔离价值不建接口 |
| Domain Policy | 授权、权益、Scope、资格、金额规则 | 确定性、默认拒绝、强类型结果、可单测 |
| Registry | 根据稳定 key 选择多个真实 Strategy/Adapter | 重复/未知 key 失败；只有一个实现时不创建 |
| Outbox/Inbox/Delivery | 提交后执行和外部至少一次投递 | 事实同事务落库、租约领取、消费者幂等、可恢复 |
| Ledger（账本） | 额度、计费、支付与对账 | 追加事实、金额精确、不能以缓存余额作为权威事实 |

这些模式不能被包装成万能框架。优先复用拥有模块已有实现，不建立覆盖所有业务的通用 Workflow、Repository 或事件总线。

## 6. 映射与转换

- HTTP DTO ↔ Command/View、Persistence Record ↔ 模型、供应商 DTO ↔ 内部类型使用纯 Mapper/Assembler。
- Mapper 不查询数据库、不读取安全上下文、不发网络请求、不开启事务。
- 字段少且只使用一次时直接显式构造，不创建 Mapper 类。
- 生成 DTO 不进入 Domain；边界处转换为领域/应用值。

Mapper/Assembler 是职责名称，不属于 GoF 23 种。不能为了满足“使用设计模式”要求强行增加转换层。

## 7. 常见功能模式选择矩阵

| 功能 | 推荐模式 | 不使用 |
|---|---|---|
| 资源生命周期状态 | State + Domain Policy + 数据库条件更新 | 散落状态判断、内存锁保护分布式事实 |
| 资源额度/支付账务 | Ledger + Policy + Command/Operation + Outbox/对账 | 可变余额缓存、Exactly Once 假设 |
| 支付/AI/邮件渠道 | Adapter；第二实现后 Strategy+Registry | 单实现先建插件框架 |
| 生命周期/版本升级 | Command + Memento 快照 + 持久化 Operation | 请求线程长事务、内存回滚 |
| 跨系统 API | Proxy + Adapter + 授权关系 + 短期凭据 | 调用方指定任意 Provider URL |
| 跨系统事件 | Observer（进程内）或 Outbox/Inbox/Delivery（可靠） | 仅进程内 Observer 承担外部投递 |
| 模块发布/审核 | State + Command + 追加事实 | 原地覆盖历史状态 |
| 普通查询 | 参数化 Query + View/Facade | 万能 Repository/Specification 框架 |

## 8. 禁止模式

- BaseController、BaseService、万能 CRUD、通用 Workflow Engine；
- 手写 Singleton、Service Locator、全局可变注册表；
- 反射扫描或字符串驱动的万能 Handler/Pipeline/Command Bus；
- 为未来可能存在的实现预建 Factory、SPI、插件系统；
- 用 Decorator/AOP 隐藏鉴权、租户和金额规则；
- 用 Observer/事件替代必须原子完成的强一致调用；
- 用 Strategy 消除简单 `switch`，却让有限状态不再穷尽；
- 为“凑齐 23 种”在代码中引入没有真实问题的模式。

## 9. 评审清单

- [ ] 能说清待解决的问题、变化点和为何直接方案不足。
- [ ] 已从 23 种模式中选择最小合适模式，或明确判定无需模式。
- [ ] 增加的接口/类型有真实隔离价值，没有一层空转发。
- [ ] 状态、错误、顺序、幂等和资源上限可以测试。
- [ ] 外部 DTO/Secret 留在 Adapter，Domain 不依赖框架。
- [ ] 可靠副作用使用持久化事实，没有用内存事件冒充队列。
- [ ] 删除模式后如果代码更清晰且约束不减弱，应删除模式。

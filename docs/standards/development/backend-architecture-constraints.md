# 后端架构约束与自动化门禁

## 1. 目标

本文说明如何把[架构模式选择规范](architecture-pattern-selection.md)、[Java 代码组织规范](java-code-organization.md)以及采用项目的架构 Profile 转换为失败关闭的自动化门禁。它不声明具体应用名、根包、模块清单、数据库、构建命令或交付阶段。

采用项目必须明确：

- 可执行交付物和组合根；
- 模块公开面、允许依赖和数据所有权；
- 所采用的 Web、持久化、消息与外部客户端技术；
- 构建生命周期中的统一检查入口；
- 暂时例外及其 Owner、测试和移除条件。

架构测试默认放在被检查交付物自己的测试源集。只有多个交付物确需共享扫描逻辑时才抽取构建期测试组件；测试组件不得进入生产制品。

## 2. 门禁工具边界

| 工具类别 | 负责 | 不负责 |
|---|---|---|
| Java 编译器 | 类型、可见性、泛型、函数式接口合法性 | 模块业务方向 |
| 格式/静态检查 | 花括号、import、基础源码格式、已知危险 API | 领域状态和数据所有权 |
| Javadoc/源码门禁 | DocLint、必写对象、参数标签和元数据格式 | 文档业务描述是否真实 |
| 模块/架构测试 | 模块发现、循环、包依赖、公开签名和组合根数量 | 运行时 SQL、授权和并发行为 |
| 构建工具 | 依赖作用域、生产类路径、生成物和制品内容 | 领域不变量 |
| 数据库集成测试 | 约束、锁、并发、迁移和隔离 | Java 包依赖 |
| 契约/安全测试 | 身份、权限、Schema、幂等和越权 | 源码格式 |

SOLID、设计模式和算法选择不能全部由静态扫描可靠判断。只有低误报、目标非空且表达真实风险的规则才进入 CI；职责是否单一、抽象是否必要、模式是否滥用及复杂度是否有界由评审清单补足。禁止用类行数、名称后缀或单实现数量等脆弱启发式代替设计判断。

## 3. 门禁启用顺序

### 3.1 首个 Java 交付物

- 从首次提交起启用编译、测试、格式/静态检查和 Javadoc 校验。
- 根构建只聚合当前已存在的子项目，不能依赖未来模块或空目录。
- CLI、Library、Web Application 和 Worker 按真实交付类型应用不同规则，不能强制每个项目都有 Web Launcher。
- 自动规则必须有正向目标或故意违规夹具，扫描为空时失败。

### 3.2 模块边界形成后

1. 模块模型非空并包含 Profile 声明的已实现模块；
2. 模块图无循环；
3. 跨模块只访问公开面或显式 Named Interface；
4. 允许依赖精确到真实目标，禁止 `*` 或全模块放开；
5. 公共签名不泄漏其他模块内部类型或基础设施类型。

使用 Spring Modulith 时应执行非空 `ApplicationModules.verify()`；使用其他模块系统时提供等价的发现、循环和内部访问检查。

### 3.3 可执行应用形成后

- 每个交付物的组合根数量由项目 Profile 明确并自动断言；领域模块不得依赖组合根内部配置。
- 生产运行类路径不包含 Testcontainers、ArchUnit、测试 Fixture、Codegen/Meta 或其他仅构建期依赖。
- Fake、Stub、Fixture 和测试数据构造器只存在于测试源码/测试交付物；门禁检查真实依赖或制品内容，不只扫描类名前缀。
- 发行目录的 JAR、依赖、脚本和配置布局由交付方式测试验证。

## 4. 分层与公开面

采用 `api/application/domain/infrastructure` 结构时，默认门禁如下：

| 包 | 禁止依赖 |
|---|---|
| `..domain..` | Web 框架、数据库实现、网络客户端、供应商 DTO、其他模块内部包 |
| `..api..` | 数据库实现、Servlet/框架请求对象、供应商 SDK、其他模块内部包 |
| `..application..` | MVC Controller、供应商 DTO、其他模块持久化实现 |
| `..shared..` | 任意业务模块和有状态框架组件 |

跨模块公开签名禁止裸 `Object`、无约束 Map、原始泛型、数据库 Record/Query/Connection、供应商 DTO、框架 HTTP 类型和可变数组。真正开放的 JSON 扩展点使用受 Schema 约束的值，并由拥有模块解析。

规则应针对依赖方向和类型所有权，不通过强制每层接口、DTO 或固定后缀制造形式架构。

## 5. 数据所有权门禁

- 每张表或集合只有一个 owning module；其他模块通过拥有方公开 API 访问。
- 数据库生成类型和持久化实现只允许 owning module 的 infrastructure 使用。
- Domain、公开 API、Controller 和事件不能暴露查询对象、连接、事务或生成表类型。
- 项目选择一种主业务持久化方式；第二种方式只允许精确、可测试的例外，不能形成双栈。
- 手写 SQL、直接连接 API、数据库特有注解和锁原语属于高风险入口，出现真实使用者后建立精确到类型/语句的允许集合。
- 数据隔离、唯一性和状态条件不能只靠入口层过滤，必须有持久化约束或条件更新测试。

如果采用代码生成，生成目录必须独立；只排除生成源码，不对手写源码做全局 suppression。Codegen 与 Meta 依赖不能进入生产类路径。

## 6. 外部适配器门禁

- 网络客户端、消息客户端和供应商 SDK 只出现在 Profile 批准的 infrastructure Adapter。
- Domain、公开 API 和普通 Application 方法不泄漏响应式、Servlet、SDK 或供应商类型。
- Secret 的解密和使用只发生在可信 Adapter，不能进入普通 DTO、事件、日志或跨模块 API。
- 本地数据库事务内不得调用远程系统；需要可靠执行时先持久化 Operation/Outbox，提交后调用。
- 重试只用于幂等且可重试操作，并有次数、退避、抖动、总时限和结果未知路径。

使用响应式服务端、虚拟线程或其他并发模型时，由项目 Profile 明确允许包、资源上限和验证方式，不在通用门禁中假定单一模型。

## 7. Controller 与契约门禁

采用 Contract First 时至少自动验证：

- 契约文件是唯一 Wire Contract 真源，生产源码没有反向生成的第二套描述；
- 每个 Operation 有稳定、唯一标识，GET/HEAD 不声明请求体；
- 实际映射和有效契约双向存在，比较 Method、规范化 Path、参数位置、请求体和成功响应；
- 每个映射方法具有项目要求的 Javadoc，Java 参数和 `@param` 一致；
- 可信 Principal、Trace Context、租户/资源归属等服务端上下文没有被伪装成客户端输入；
- 生成客户端能够编译，生成物不提交且没有手写传输 DTO 分叉。

如果采用 Code First，必须由项目 ADR 声明唯一真源、发布兼容和生成物流程，不能在同一应用混用两种所有权。

## 8. 运行时不变量测试

以下规则不能只用静态架构测试证明：

| 规则 | 验证方式 |
|---|---|
| 租户/资源归属不可跨边界 | 真实身份的正向与越权负向测试 |
| Migration 是唯一 Schema 入口 | 配置测试 + 空库迁移 |
| 外部调用不在本地事务 | Adapter 调用顺序或事务探针 |
| Operation/Outbox/Delivery 可恢复 | 多线程/多进程数据库测试 |
| 幂等键、重复和结果未知正确 | 重放、并发和故障注入测试 |
| 生产制品不含测试/生成依赖 | 运行类路径和发行制品检查 |

业务规则、数据库特性和锁语义必须在实际采用的数据库上测试，不使用行为不兼容的内存替代品冒充通过。

## 9. Checkstyle 基线

Java 项目应启用 Checkstyle 或等价静态检查，至少覆盖主源码和测试源码：

```xml
<module name="Checker">
  <module name="FileTabCharacter"/>
  <module name="NewlineAtEndOfFile"/>
  <module name="TreeWalker">
    <module name="NeedBraces">
      <property name="allowSingleLineStatement" value="false"/>
      <property name="allowEmptyLoopBody" value="false"/>
    </module>
    <module name="AvoidStarImport"/>
    <module name="EmptyCatchBlock"/>
    <module name="OneStatementPerLine"/>
    <module name="OuterTypeFilename"/>
  </module>
</module>
```

所有控制语句必须带花括号。生成源码放入独立目录并只对该目录排除；不得对手写源码使用全局 suppression。

Lambda 适用性不能从字节码可靠判断，也不能机械把循环改成 Stream。编译器校验 `@FunctionalInterface` 合法性，评审负责发现可直接改写的匿名函数式实现和副作用 Stream；没有低误报方案时不为该项新增脆弱源码扫描器。

## 10. CI 聚合

采用项目必须提供一个统一检查入口（例如 Gradle `check` 或 Maven `verify`），聚合能够在构建内运行的：

- 编译、格式/静态检查、单元与集成测试；
- Javadoc/源码元数据；
- 模块和架构规则；
- OpenAPI/Schema/事件契约；
- Migration/Codegen/数据库验证；
- 生产类路径和发行制品内容。

Secret、镜像、许可证或基础设施扫描可以由 CI 显式执行，但结果必须和精确 Commit 绑定。禁止让同一昂贵任务通过多个聚合入口重复运行，也不能把任务跳过写成通过。

## 11. 例外规则

架构例外必须同时满足：

1. 精确到包、类型、语句或生成目录；
2. 说明正常公开 API 为什么无法表达；
3. 有正向和负向测试，扫描目标非空；
4. 记录 Owner、到期条件和移除方式；
5. 不包含全域放行、通配依赖或“先跳过以后再说”。

规则修改必须与触发它的代码同一提交，并说明是边界变化还是测试修正。禁止仅删除失败规则让构建变绿。

## 12. 验收清单

- [ ] 项目 Profile 已声明交付物、组合根、模块、技术栈和统一检查入口。
- [ ] 模块模型非空、无循环、内部包没有跨模块访问。
- [ ] Domain/API 不泄漏框架、持久化或供应商类型。
- [ ] 数据生成类型和持久化入口留在拥有模块。
- [ ] 外部客户端只存在于批准的 Adapter，远程调用不在本地事务中。
- [ ] 生产运行类路径和发行制品不包含测试、Fixture 或 Codegen 依赖。
- [ ] 契约与实现双向一致，生成客户端能够编译。
- [ ] 架构测试对空目标、错误包名和失效允许列表失败关闭。
- [ ] 功能采用满足当前复杂度的最小架构，没有单实现 SPI、万能模式或无界查询。

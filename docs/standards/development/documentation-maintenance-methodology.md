# 工程文档体系与维护方法论

> 文档状态：已生效，可作为新项目文档治理基线  
> 适用范围：需要持续维护需求、设计、实现、验证和运行知识的软件工程项目  
> 适用对象：产品负责人、架构师、研发、测试、运维、安全和项目负责人  

## 1. 目的与适用范围

本文定义一套与具体产品、组织、技术栈和阶段编号无关的工程文档维护方法：用最少的一组文档分别承载长期边界、阶段设计、架构决策、执行状态、验证证据和运行处置，并让它们随实现同步演进。

采用本文时只复用结构、状态和维护规则。项目名称、业务模型、目录、阶段、技术版本、质量门和角色必须由采用项目自行定义。

## 2. 核心方法

文档体系的核心不是“写一份完整大文档”，而是按事实的变化速度和责任分层：

1. **一类事实一个真源**：产品边界、架构、契约、实施状态和运行步骤分别维护，其他位置只链接和摘要。
2. **设计与证据分离**：阶段文档说明应当实现什么，完成计划记录实际交付了什么，当前状态只引用可追溯证据。
3. **文档状态与功能状态分离**：设计已生效不代表代码已实现，本地测试通过不代表受控验收或生产就绪。
4. **契约先行、实现闭合**：外部契约先改，随后同步实现、生成客户端、测试和受影响文档。
5. **历史可追溯，当前状态唯一**：完成计划归档保留，当前结论集中在文档索引中，过时内容明确标注历史边界。
6. **运维属于交付**：有外部副作用、异步任务、凭据、高风险数据变更或跨系统调用时，Runbook 和恢复验证进入完成定义。
7. **按证据演进**：未来架构、基础设施和复杂能力只写启动条件，不提前建设空接口或空文档体系。

## 3. 通用工程文档分层

| 层次 | 推荐位置 | 主要责任 | 生命周期 |
|---|---|---|---|
| 导航与状态 | `docs/README.md` | 阅读顺序、全量入口、状态规则和当前结论 | 持续更新 |
| 项目总纲 | `docs/00-project-master-plan.md` | 项目定义、术语、长期不变量、非目标、路线图、质量门和完成定义 | 低频演进 |
| 架构基线 | `docs/architecture-and-technology-selection.md` | 工程结构、运行时、数据、身份、测试、部署及拆分门槛 | 架构变化时更新 |
| 项目绑定 | `docs/project-development-profile.md` | 把通用规范绑定到当前项目的技术栈、目录、模块、命令和例外 | 随工程基线更新 |
| 开发规范 | `docs/development/` | 代码、设计、契约、数据库、门禁和协作的可复用规则 | 跨项目复用，按规则演进 |
| 开发手册 | `docs/development-manual.md` | 启动、日常任务流程、调试、构建、验收和协作操作 | 工具或流程变化时更新 |
| 阶段设计 | `docs/phases/<phase>.md` | 使用者结果、范围、模型、接口、数据、安全、测试和退出门槛 | 基线化后维护真实设计 |
| 架构决策 | `docs/decisions/README.md`、`0000-template.md`、`NNNN-<decision>.md` | 决策索引、模板，以及背景、决策、后果和未选择方案 | Accepted 后保留历史；变化用新 ADR |
| 当前阶段切片 | `docs/plans/current-stage-plan.md` | 唯一正在实施的阶段、切片、状态、依赖、验证要求和剩余门槛 | 执行期高频更新；阶段完成后重命名归档 |
| 完成证据 | `docs/plans/completed/<stage>-implementation-plan.md` | 已完成阶段的切片、命令、测试、验收和提交证据 | 从当前阶段切片移动而来，只修事实错误 |
| 运维处置 | `docs/operations/<runbook>.md` | 监控、诊断、止损、恢复、回滚、演练和事件关闭 | 随运行机制更新 |

并非每个项目从第一天起都需要全部目录。同一能力可以同时拥有阶段设计、实施计划、ADR 和 Runbook，但每份文档回答不同问题，不能相互复制成多份真源。

## 4. 事实归属与优先级

### 4.1 一类事实一个真源

| 要回答的问题 | 唯一真源 | 其他文档的写法 |
|---|---|---|
| 产品是什么、什么永远不做 | 总纲 | 摘要并链接总纲 |
| 工程如何组织、何时拆分 | 架构基线 | Profile 只填写项目具体值 |
| 当前项目使用什么版本、目录和门禁 | 项目 Profile | 通用规范不写项目专属值 |
| HTTP、事件或数据格式 | 仓库中的 OpenAPI、JSON Schema 或其他可执行契约 | 文档解释语义并链接契约，不复制第二套可执行定义 |
| 某阶段要交付什么 | 阶段文档 | 计划引用稳定需求 ID |
| 为什么选择某个跨领域方案 | ADR | 阶段文档只引用决策结论 |
| 当前切片做到哪里 | `plans/current-stage-plan.md` | README 只写里程碑摘要 |
| 实际运行过哪些验证 | 完成计划 | 不把计划命令写成已通过证据 |
| 出故障如何诊断和恢复 | Runbook | 设计文档只声明必须具备该能力 |
| 整体当前能否使用或发布 | README 当前状态 | 以完成计划中的验证证据支撑，不由单个绿色构建替代 |

### 4.2 冲突处理顺序

发生冲突时按以下顺序处理：

1. 安全、隐私、数据完整性、隔离边界和已经发布的外部契约；
2. 产品总纲和已接受 ADR；
3. 当前阶段设计与项目 Profile；
4. 通用开发规范；
5. 实施计划、示例和局部偏好。

若实现与文档冲突，不应静默选择更方便的一方。先确认哪一方是对应事实的真源，再在同一变更中修正另一方；已发布契约需要按兼容和版本策略演进。

## 5. 各类文档的最小结构

### 5.1 所有规范性文档

开头至少包含：

- 文档状态；
- 实施状态或“本文不记录实施状态”的说明；
- 适用范围和目标读者；
- 上位真源、依赖文档和相关 ADR/Runbook；
- 最近发生实质变化的日期，仅在确有维护价值时记录。

正文只保留当前读者完成任务所需的章节。常用顺序是：目标 → 范围与非目标 → 术语和不变量 → 模型/流程 → 契约和数据 → 安全与失败语义 → 测试验收 → 运维回滚 → 风险和后续门禁。

### 5.2 阶段设计

至少回答：

1. 用户能得到什么结果；
2. 本期做什么、不做什么，依赖哪些前置事实；
3. 角色、术语、数据所有权和关键不变量是什么；
4. 状态机、主流程和异常流程如何收敛；
5. API、事件、数据库、前端和模块边界如何配合；
6. 身份、权限、隔离、幂等、并发、重放和结果未知如何处理；
7. 哪些自动化、真实环境和人工验收构成退出门槛；
8. 哪些事项延后，以及用什么证据启动。

复杂能力使用稳定需求 ID，使计划、测试、验收和提交能够反向追踪；简单能力不需要为了形式虚构编号。

### 5.3 ADR

ADR 目录由三类文件组成：

- `decisions/README.md`：维护状态规则、当前 Accepted 决策索引和下一个可用编号；
- `decisions/0000-template.md`：提供统一模板，不计入决策数量；
- `decisions/NNNN-<decision>.md`：保存一项可独立解释的架构决策。

本文是 ADR 通用结构的真源；采用项目从下面的生成基线创建本地文件。项目可以增加必要字段，但不得删除状态、取代关系、验证和后续动作等强制内容。

#### 5.3.1 `decisions/README.md` 生成基线

~~~markdown
# 架构决策记录

> 文档状态：已生效，作为当前 ADR 索引与维护规则  
> 适用范围：影响多个模块、外部兼容、数据所有权、部署边界、安全模型或长期技术基线的决策  

本目录保存当前项目的架构决策记录。ADR 解释“为什么这样选择”，不替代阶段设计、当前阶段切片、外部契约或完成证据。ADR 被接受只表示决策生效，不表示对应实现已经交付。

## 1. 状态与编号

| 状态 | 含义 |
|---|---|
| `Proposed` | 正在评审，不能作为当前架构事实 |
| `Accepted` | 已接受并成为当前决策；实现仍需由计划、代码和验证证据确认 |
| `Superseded` | 已被后续 ADR 取代；正文保留历史，并链接取代它的 ADR |
| `Rejected` | 已评审但未采用；保留理由，不能作为实现依据 |

- 文件使用 `NNNN-short-title.md`，编号只递增、不复用。
- `0000-template.md` 是模板，不计入决策数量。
- Accepted ADR 不通过重写历史改变核心结论；需要反转时新增 ADR，并维护双方的取代关系。
- 日常实现细节不创建 ADR；局部方案由阶段设计或当前阶段切片记录。

## 2. 模板

- [ADR 模板](0000-template.md)

## 3. 当前决策

| ADR | 状态 | 当前结论 |
|---|---|---|
| [ADR-NNNN：标题](NNNN-short-title.md) | Accepted | 一句话说明当前结论 |

## 4. 新增或取代决策

1. 复制 [ADR 模板](0000-template.md)，使用下一个未占用编号；当前下一个编号为 `{NEXT_ADR_NUMBER}`。
2. 先以 `Proposed` 记录问题、约束、候选方案和验证要求。
3. 评审通过后改为 `Accepted`，同时更新本索引及受影响的总纲、架构、阶段设计或项目 Profile。
4. 实施工作进入 `plans/current-stage-plan.md`；实际完成状态只依据代码、契约、测试和验收证据更新。
5. 取代旧决策时创建新 ADR，把旧 ADR 标为 `Superseded`，并在两份文档中建立双向链接。
~~~

`当前决策` 和 `{NEXT_ADR_NUMBER}` 由采用项目维护，不能从其他项目复制现值。Rejected 和 Superseded ADR 保留历史，但不列为当前生效决策。

#### 5.3.2 `decisions/0000-template.md` 生成基线

~~~markdown
# ADR-NNNN：标题

> 状态：Proposed  
> 日期：YYYY-MM-DD  
> 决策范围：  
> 决策人：  
> 关联文档：  
> 取代：无  
> 被取代：无  

## 1. 背景

说明触发决策的问题、已知约束和已有证据。不要把候选方案写成既成事实，也不要在这里复制完整实施设计。

## 2. 决策

清晰写出选择、适用范围、非目标和必须保持的不变量。能够由外部契约或项目 Profile 表达的具体值，应链接其真源而不是复制第二份定义。

## 3. 后果

说明正向收益、成本、风险、兼容影响、迁移路径和回滚边界。

## 4. 未选择方案

列出真正评估过的候选项及未选择理由。没有实际评估的方案不要为了凑格式补写。

## 5. 验证

列出让该 ADR 从 `Proposed` 进入 `Accepted` 所需的测试、PoC、基准、兼容检查或评审证据。接受决策不等于实现完成；实现状态由关联计划和实际验证记录维护。

## 6. 后续动作

列出责任明确、可验证的实施项，并链接 `plans/current-stage-plan.md`。阶段完成后改链归档入口，不在 ADR 中维护第二份高频任务清单。
~~~

#### 5.3.3 同步与演进规则

- 普通实现细节不写 ADR。只有影响多个模块、外部兼容、数据所有权、部署边界、安全模型或长期技术基线的决定才需要 ADR。
- Accepted 表示决策生效，不表示对应功能已经实现或发布。
- 新增前先搜索现有 ADR；已有决策能够解释当前边界时直接引用。
- 反转旧决策时新增 ADR，不重写旧 ADR 的核心结论。
- 本方法论的强制字段或状态规则变化时，采用项目应在同一变更中同步本地 `decisions/README.md` 和 `0000-template.md`；项目当前决策清单仍只在本地索引维护。

### 5.4 实施计划与完成归档

`plans/` 在实施期间只保留一份 `current-stage-plan.md`，表示唯一正在实施的当前阶段。它按可独立验收的切片组织，每个切片至少记录：

- 目标和范围；
- 依赖的阶段需求或 ADR；
- 契约、实现、测试、文档和运维交付物；
- 最小验证及真实环境门槛；
- 当前状态和明确剩余项。

当前阶段完成后执行一次明确的阶段切换：

1. 在 `current-stage-plan.md` 中关闭全部必需切片，补齐实际验证、验收和剩余边界；
2. 按阶段含义重命名为 `<stage>-implementation-plan.md`，并移动到 `plans/completed/`；
3. 同步 README、阶段文档和相对链接，使归档文件成为该阶段的完成证据；
4. 为下一阶段重新创建唯一的 `plans/current-stage-plan.md`，只包含下一阶段的目标和切片。

阶段归档与下一阶段计划初始化应在同一次文档切换中完成，避免 `plans/` 同时存在多份“当前计划”或长期没有当前计划。归档表示“执行记录完成”，不自动表示正式发布或生产可用。

### 5.5 Runbook

Runbook 面向值班和发布现场，章节优先按操作顺序组织：

1. 适用边界、权限和保密要求；
2. 日常健康检查和建议告警；
3. 从现象到事实的诊断顺序；
4. 止损、重试、补偿、恢复和回滚步骤；
5. 幂等、结果未知和禁止操作；
6. 备份恢复、密钥轮换或故障演练；
7. 发布门禁和事件关闭证据。

Runbook 不复制完整架构设计，也不把直接改库、关闭鉴权或泄漏 Secret 作为常规恢复手段。

## 6. 状态模型

### 6.1 文档状态

| 状态 | 含义 |
|---|---|
| 已生效 | 当前研发和评审必须遵守 |
| 已基线化 | 可直接据此实施；后续通过评审修订 |
| 规划草案 | 尚未进入实施，可根据前置证据调整 |
| 条件演进草案 | 只有量化门禁满足后才启动 |
| 已归档 | 保留历史和证据，不再承担当前计划职责 |
| 已废弃 | 已有替代真源；保留时必须标明替代文档和截止边界 |

### 6.2 实施与交付状态

实施状态可使用 `✅`、`🚧`、`⏸️`、`⛔`，但文字必须同时说明边界。至少区分以下结论：

1. 设计或源码存在；
2. 本地自动化验证通过；
3. 真实客户端、外部依赖或代表性环境可用；
4. 正式验收完成；
5. 制品已发布或功能已部署；
6. 生产发布条件满足；
7. 当前工作区是否具备提交条件。

状态更新必须附证据或明确剩余门槛。不得用“计划已写”“构建绿色”或“页面可打开”替代更高层级结论。

## 7. 文档随项目演进的闭环

### 7.1 从需求到归档

```text
产品目标与长期边界
  → 总纲 / 架构基线
  → 阶段设计
  → 必要的 ADR
  → plans/current-stage-plan.md 当前阶段切片
  → 契约 / 实现 / 测试 / Runbook
  → 实际验证与验收证据
  → 重命名并移动到 plans/completed/<stage>-implementation-plan.md
  → README 当前状态与阶段文档回链
  → 创建下一阶段 plans/current-stage-plan.md
```

设计变更发生在实现前；实现过程中只校准必要事实；完成后归档证据。任何一步发现架构假设不成立，都回到拥有该事实的文档修订，而不是在计划、代码注释和聊天记录中产生旁路规则。

### 7.2 变更联动

| 变更类型 | 同一变更中应更新或验证 |
|---|---|
| 产品边界、术语或跨阶段不变量 | 总纲、受影响阶段、契约和验收 |
| 架构、交付物、模块或数据所有权 | 架构基线、项目 Profile、ADR、架构门禁 |
| OpenAPI、Schema 或事件 | 契约真源、生成客户端、兼容检查、阶段文档和契约测试 |
| 表、索引、约束或状态事实 | Migration、数据设计、生成输入、数据库测试和恢复说明 |
| 身份、权限、数据隔离、金额或额度 | 威胁边界、负向测试、操作记录和 Runbook |
| 外部依赖、异步任务或可靠副作用 | 失败语义、指标告警、补偿/重试和 Runbook |
| 版本、构建或开发流程 | 项目 Profile、开发手册、CI 和兼容验证 |
| 阶段或切片完成 | 完成计划、阶段实施状态和 README 当前结论 |

没有对应变化时不要机械修改所有文档。例如没有 API 变化就不改 OpenAPI，没有数据库变化就不创建空 Migration，没有跨领域长期决策就不新增 ADR。

### 7.3 归档、废弃与删除

- 阶段文档保留当期设计和当前仍有效的维护边界；已经移除的运行物必须在文档头明确标成历史，不伪装成当前能力。
- 当前阶段切片重命名并移动归档，不复制一份“完成版”；移动后同步导航和相对链接，再创建下一阶段切片文档。
- 被新规范完全替代的旧文档先写替代关系，再迁移引用，最后删除或标记废弃。
- 删除前同时检查工作区和当前 `HEAD` 中的引用；零引用时不做额外补丁。
- README 只保留当前入口和摘要，不堆放详细执行记录。

## 8. 文档体系的渐进式演进

| 项目状态 | 文档动作 | 控制原则 |
|---|---|---|
| 项目启动 | 建立 README、总纲、架构基线、Profile 和首个阶段文档 | 先冻结边界和交付顺序，不预建完整文档树 |
| 开始实施 | 建立唯一的 `plans/current-stage-plan.md` 并拆分可验收切片 | 计划服务于执行，阶段文档服务于设计 |
| 出现长期架构取舍 | 建立 ADR 索引和模板，按需增加首个 ADR | 只记录跨模块、外部兼容或长期基线决策 |
| 进入持续运行 | 为真实故障和恢复责任增加 Runbook | 先有运行责任，再增加运维文档 |
| 阶段完成 | 把当前计划按阶段名称重命名到 `plans/completed/`，回写状态并创建下一阶段当前计划 | 归档与下一阶段初始化在同一次切换中完成 |
| 规则可跨项目复用 | 抽取通用开发规范，项目具体值保留在 Profile | 通用规则不携带项目名称、版本和目录 |
| 文档被替代 | 迁移引用，标明替代关系，再归档或删除 | 更新导航并验证当前工作区和 `HEAD` 引用 |

稳定形态是 `plans/` 中始终只有一份 `current-stage-plan.md` 承担当前执行职责。完成后它以稳定的阶段名称进入 `plans/completed/`，原路径随即用于下一阶段，历史证据从阶段文档和 README 回链。

## 9. 新项目的最小落地

新项目第一天只建立能承担当前事实的最小集合：

```text
docs/
├── README.md
├── 00-project-master-plan.md
├── architecture-and-technology-selection.md
├── project-development-profile.md
├── development/
│   └── README.md
├── phases/
│   └── 01-<first-deliverable>.md
└── plans/
    ├── current-stage-plan.md
    └── completed/
```

按以下顺序扩展：

1. README 建阅读顺序、状态词汇和当前结论；
2. 总纲冻结产品边界、术语、非目标、路线和质量门；
3. 架构文档确定工程、数据、身份、部署和演进门槛；
4. Profile 绑定技术版本、目录、构建命令和项目例外；
5. 第一阶段文档写用户结果、范围、设计和退出门槛；
6. 在唯一的 `current-stage-plan.md` 中拆分最小可验收切片；
7. 出现真实跨领域决策时建立 `decisions/README.md` 和 `0000-template.md`，再增加首个 ADR；
8. 出现需要值班处置的运行风险时增加 Runbook；
9. 阶段完成后重命名归档当前计划、更新 README，并创建下一阶段的 `current-stage-plan.md`。

额外阶段、复杂基础设施决策、运维文档和模板都等真实需求出现后再建。

## 10. 维护检查清单

提交文档变更前检查：

- [ ] 新内容属于正确文档类型，没有创建第二真源；
- [ ] 文档状态、实施状态和验证边界分开表达；
- [ ] 范围、非目标、前置依赖和退出门槛清楚；
- [ ] 计划项引用稳定需求或明确能力边界；
- [ ] `plans/` 只有一份 `current-stage-plan.md`；阶段完成时已重命名归档并创建下一阶段当前计划；
- [ ] 新增 ADR 使用未占用编号、更新索引；Accepted 没有冒充实现完成，取代关系保持双向；
- [ ] 项目内 `decisions/README.md` 和 `0000-template.md` 与本文生成基线一致；当前决策和下一个编号只在本地索引维护；
- [ ] 契约、实现、测试、Runbook 和状态按变更影响同步；
- [ ] “已通过”只对应本次或可追溯的实际证据，未运行项明确列出；
- [ ] 历史内容标明时间和适用边界，不冒充当前事实；
- [ ] 相对链接、移动后的路径和 README 导航有效；
- [ ] 文档中没有 Token、密码、Secret、个人敏感信息或受限业务载荷；
- [ ] 连续 `>` 元信息行保留两个 ASCII 空格硬换行；
- [ ] `git diff --check` 通过，差异没有混入无关格式化或其他任务内容。

最重要的验收标准只有一个：读者能够从 README 找到唯一真源，并从设计一路追踪到实现、验证、运行和当前结论，而不需要猜哪份文档最新。
